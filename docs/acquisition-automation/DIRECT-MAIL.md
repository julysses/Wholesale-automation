# Direct mail — implementation and release boundaries

The pure preparation module in `tools/acquisition_mail.py` accepts typed, trusted repository snapshots from `schemas/acquisition_mail.py`. It prepares a review proposal; it performs no I/O, reservation, approval, scheduling or fulfillment. No API exposes these models as caller-provided authorization. There is no selected vendor or active mail campaign.

## Current preparation behavior

- Rank scored Dallas/Collin, TX properties deterministically, with stable property-ID tie breaking. Missing score remains missing. Owner status must be living; deceased or unknown status requires review. No automatic estate-recipient inference.
- Require unexpired address verification with an evidence reference and canonical recipient/delivery-point identity preserving unit distinctions. The module does not validate addresses itself or treat punctuation-stripped addresses as verified.
- Require clear contact preferences and a nonexpired ALLOW eligibility receipt. BLOCK/REVIEW selects no piece. The current shared eligibility service still returns BLOCK/REVIEW; synthetic ALLOW fixtures test the future boundary, not current permission.
- Collapse identical property snapshots, reject conflicting duplicates, and deduplicate selected recipient/address identities. Cadence includes jobs across campaigns. Active and unknown submissions, or failed/cancelled jobs without authoritative nonfulfillment evidence, hold indefinitely. Fulfilled pieces age out of cadence at the configured interval, but remain charged against lifetime campaign budget.
- Costs require USD and use integer cents and a positive, unexpired unit quote. Existing campaign commitments reduce the available budget. Unknown costs cannot be omitted or silently defaulted to zero. Existing proposals are not reservations. Failed/cancelled jobs release budget only with nonfulfillment evidence; a transport failure alone is insufficient.
- Require a complete, recent history snapshot across all workspace campaigns/dates. Incomplete/stale snapshots select nothing and report committed/remaining amounts as unknown, not zero. Five minutes allows snapshot transport latency only; it grants no execution window. Workspace mismatch, duplicate history jobs and future timestamps reject the snapshot.
- Preserve template/version, letter/postcard format, quote/vendor and tracked destination references. Each proposed piece receives a stable batch/property UUID tracking ID. A canonical snapshot digest binds the selection inputs for future immutable persistence; changed inputs must not reuse a persisted batch ID without conflict handling. No raw postal address or recipient key is returned in the proposal.

## Required integration before MAIL release acceptance

1. Reinspect current deployed schema, migration history, constraints, RLS and equivalent entities before creating additive mail SQL. The prior inventory found no dedicated mail_jobs table; this module does not change that inventory into a migration.
2. Load snapshots under actual membership/role authorization from canonical property/owner relationships, approved template/destination versions, selected vendor verification/quote evidence and shared eligibility. Resolve postal preferences across matching owner/address identities, including inbound direct_mail/all restrictions. Client assertions must never supply clear preferences, ALLOW, verification, quote validity or history completeness.
3. Persist proposed batches and immutable selected inputs, tracking IDs, audit history and exact idempotency fingerprints. Implement atomic approval/reservation across campaign budget, property cadence and recipient deduplication. This pure algorithm offers no concurrency protection and must not be used as an execution lock.
4. Select a vendor; implement sandbox/proof creation, idempotent submission, signed status receipts and reconciliation. Establish quote coverage for print, postage, taxes and other charges, and proof of nonfulfillment before release. A provider acceptance response is not delivery.
5. Recheck current eligibility, suppressions, approved template/destination, cost/budget and frequency atomically before execution. Bind authorization to exact batch contents and authorized approval. Unknown outcomes retain reservations. Enforce sequential channel activation and separate campaign approval.
6. Verify populated upgrades, workspace/role RLS, simultaneous approvals/submissions, replay/lost responses, postal preference matching, refunds/nonfulfillment and vendor proof reconciliation end to end. Only then request campaign approval. A daily scheduler may initially prepare proposals only.

No counsel-approved mail policy, final mailing frequency, vendor, template, tracked destination or budget is invented by this implementation. These are configuration and release dependencies. Production, SMS schedules, provider routing and live outreach remain unchanged.

## Authenticated draft API

`POST /api/acquisition/workspaces/{workspace_id}/campaigns/{campaign_id}/mail-templates` accepts request id, template id, expected_version, name, letter/postcard format, phone/landing_page tracking mode and body. It forwards the signed-in user's bearer token and public key to the controlled SQL RPC. Workspace and campaign come only from the URL; extra authority/status fields are rejected. Required tracking and supported placeholders are validated before a database request. A response is confirmed only when identity, workspace, template, next integer version, draft status and false execution authority match exactly. Timeout or an invalid receipt returns an unconfirmed error with no automatic retry; clients must retain the exact request for reconciliation.

`GET` on the same path lists scoped immutable versions using bounded UUID pagination (default 20, maximum 50), with optional template_id filtering. Ordering is by row ID, not version recency: consumers must not infer the latest version from the first row. The SQL expected-version check remains authoritative. Draft text must be displayed as text, never inserted as HTML. The campaign-draft mail editor connects these endpoints with durable pending-request recovery and explicit version selection; these endpoints do not approve or render mail.

## Campaign-draft editor

Direct-mail campaign rows now expose a collapsed mail editor. Opening it loads scoped membership and bounded history with user/workspace/campaign query keys. Owners, administrators and operators can prepare letter/postcard drafts. Selecting a historical version makes the next expected version explicit; the SQL check rejects stale edits. The template body is displayed as text, including angle brackets, never executable HTML. Destination placeholders remain unbound until a separate review flow.

Each intentional save persists its exact UUID, template identity, expected version and content in sessionStorage before transmission, keyed by signed-in user/workspace/campaign. Unknown responses freeze editing and keep exact retries available after refresh, unmount or reload. A first definite rejection may clear that new pending request; rejection of an already uncertain retry preserves it. Storage failures prevent writes or preserve the unresolved request. The editor cannot approve content, select a vendor, fund campaigns or send mail.

Validation covers component behavior, full frontend regression, type/build and lint. Real-browser layout/accessibility review and real PostgREST/JWT delivery remain separate acceptance items; component tests do not establish those outcomes.

## Reviewed content binding and inert proofs

`schemas/acquisition_mail_render.py` and `tools/acquisition_mail_render.py` implement the pure content boundary for the upcoming authenticated review flow. They do not persist approvals or expose an endpoint. Repository-sourced evidence remains mandatory: a caller cannot authorize mail by submitting these models.

`content_binding` hashes the exact template identity/version/body/format/mode, company identity, destination scope/identity/version/value/verification evidence and renderer version. A human review must retain this digest. `render_mail_proof` rejects scope mismatches, destination mode mismatches, changed bindings, withdrawn/rejected reviews, revoked/expired destination evidence, future timestamps and review predating destination verification. It requires timezone-aware evidence and strict flags/version numbers.

Phone values must already be normalized E.164. Website values use a conservative HTTPS syntax with no credentials, ports, query/fragment, percent escapes, local/reserved suffixes or IP literals. This is syntax screening only: it does not establish ownership, DNS safety, absence of redirects, lawful content or functioning attribution. The authenticated destination-review workflow must supply that evidence; the renderer does not fetch websites or configure numbers.

Only the selected response placeholder is permitted. Company/property substitutions are literal, reject controls and nested placeholders, and cannot execute markup. Output includes plain text plus an escaped inert HTML fragment, with a bounded expanded length. Plain text must never be reinterpreted as HTML by a future adapter. The proof digest also binds property identity/address, per-piece tracking ID and exact review evidence, so changed recipient content or review needs another proof. It excludes preparation time for stable exact retries while checking current expiry each invocation.

Every output says `execution_authorized: false`. A content review is not campaign approval, recipient eligibility, budget/cadence reservation, vendor layout/proof approval or delivery. There is no vendor-ready design or print-quality claim. Persisting evidence, recording human approvals/withdrawals, securely storing proof content, selecting approved routing, and connecting proofs to atomic jobs remain required. Do not log property-bearing rendered content; future persistence must use access-controlled retention.

New approval requires a draft campaign and active gate; withdrawal preserves prior evidence and remains available with the activation gate off. Operators/callers/service-role invocations cannot approve. Direct insert/update/delete/truncate privileges are withheld and update/delete triggers preserve evidence.

Historical rows are evidence, not permission. A future content-proof reader must use this current projection under appropriate authorization and recheck it atomically at execution.

## Destination review screen and history

Direct-mail campaign cards now include a lazy-opening destination panel alongside mail templates. History is a bounded fixed-column projection under workspace/campaign RLS, paginated by UUID rather than recency. A historical approved row is explicitly labeled as recorded history. Selecting a destination loads its current projection separately, checks scope/shape/status/evidence dates, and displays the server check timestamp. Operators may inspect; active owners/admins with server-enforced MFA may review.

Existing approval edits require explicitly loading the current destination version. A newer version observed during refresh locks the old form until the reviewer loads it again. New approvals require a verification reference/digest, observation and expiry dates, documented reason and affirmative control/routing attestation. Withdrawal uses the current expected version plus reason and omits replacement evidence. The form is an internal evidence-entry surface; a protected artifact upload/resolver and actual control/routing validation are still required before live release.

Each request is persisted before transmission under a user/workspace/campaign session-storage key, including the destination identity and exact review body. Lost/malformed responses lock editing and retain the same request through refresh/unmount/reload. Uncertain retries remain retained after rejection; only a first definite rejection can clear a new request. Corrupt or unavailable storage fails closed. Receipt validation never treats saving an approval as mail execution permission. All text is rendered inertly and destination links are not automatically opened or fetched.

GET `/api/acquisition/workspaces/{workspace}/campaigns/{campaign}/mail-destinations` provides this historical discovery view (limit 20, maximum 50, UUID cursor). Current authorization continues to come from the per-destination current-state endpoint and ultimately fresh server checks. The screen does not approve template wording, produce vendor proofs, reserve a budget, configure providers, or fulfill mail. Browser/layout acceptance of this new destination panel remains pending; component tests are not browser evidence.

## Trusted internal proof loading — October 28, 2026

Local, unapplied migration `20261029014552_acquisition_mail_proof_context.sql` adds a read-only stable RPC that reads current content approval and the enrolled canonical property in one database statement snapshot. It requires the existing owner/admin/operator workspace/session authority, current approval and matching workspace-lead/property-lead relationship. It selects only property identity, standardized street, unit, city, state and ZIP; no owner/contact fields. Missing canonical street/city/state fails rather than substituting an unrelated legacy lead address. It performs no write, reservation, address verification or provider request.

POST `/api/acquisition/workspaces/{workspace}/campaigns/{campaign}/mail-content/{content}/proof` accepts only `lead_id`. The server loads that RPC with the user's bearer token, validates the complete projection, exact scope/source identities and shared check timestamp, and reconstructs renderer inputs from current persisted approval/preparation. Caller-supplied addresses, company names, snapshots, approvals, hashes, tracking IDs and clocks are rejected. The loader rejects snapshots older than 30 seconds or over 5 seconds ahead of the server clock, and rechecks expiry at rendering. These limits bound transport latency, never execution authority. Expired/noncurrent evidence requires refresh; malformed or mismatched projections return no proof.

Output is JSON with literal plain text and an escaped inert HTML fragment. Consumers should display the text normally, never evaluate source template text. Units are preserved explicitly; absent ZIP/unit remains absent. The subject-property address is not a verified mailing destination. `proof_kind=internal_content_preview`, `tracking_id_kind=preview_only`, and false postal/recipient/vendor/execution flags prevent mistaking this for a fulfilled piece or vendor proof. The deterministic preview UUID is scoped to workspace/campaign/content review/property and is not a mail-job tracking identifier. Responses use Cache-Control: no-store.

The loader preserves the renderer digest separately, binds the SQL preparation hash, content review identity/version/evidence digest and exact canonical property fields into a source digest, then combines both with the loader version into the returned proof digest. Changed unit/address/source evidence changes the proof digest. Unchanged reads stay deterministic apart from explicit check/render timestamps. No new approval is inferred or persisted from rendering; a saved preview becomes historical if its underlying approval changes, so later fulfillment must reload current evidence under its own atomic execution controls.

GET `/api/acquisition/workspaces/{workspace}/campaigns/{campaign}/mail-content` supplies bounded UUID-paginated history with a fixed projection and workspace/campaign RLS. Historical rows are discovery evidence only, not current approval; the per-content current-state endpoint remains separate.
