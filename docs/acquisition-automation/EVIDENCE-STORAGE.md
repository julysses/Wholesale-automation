# Acquisition evidence — private storage and verification

## Implemented byte-verification contract

- Expected workspace, campaign and purpose must match the descriptor. Revoked, expired or not-yet-created evidence is rejected before I/O. Supported initial types are PDF, PNG, JPEG and plain text; the descriptor is strict, immutable and limited to 10 MiB.
- The fixed future bucket is `acquisition-evidence`. The object key is derived from workspace UUID / artifact UUID / SHA-256, with no user filename, URL, traversal, query or mutable latest alias. This is a naming contract, not a claim that the bucket exists.
- Use the existing configured HTTPS project origin and user bearer/public key. Reject unexpected URL paths, credentials in the URL, queries/fragments and missing user authorization. No signing, service-role fallback, redirects or public URL generation.
- Stream exact raw bytes with a size ceiling, per-read timeout and a 15-second total deadline. Reject non-200/partial results, compression, incompatible media type, invalid length, truncated/oversized content and hash mismatch. Recheck retention and clock order after reading. Responses and failures do not expose document bytes, upstream error bodies, credentials or URLs.
- Success is `bytes_verified` with source identity, exact digest/size/type and check/retention timestamps. Both content approval and execution authority remain false. A byte match is not malware scanning, factual verification, legal approval, immutable-storage proof or authorization to mail.

## Implemented registry-backed verification seam

The store's internal verification method accepts only UUID artifact/workspace/campaign identities and an allowed purpose. It no longer accepts a descriptor containing expected size, hash or retention. It makes a bounded POST to the protected `acquisition_evidence_state` RPC, validates the exact projection and scope, and derives the immutable descriptor from that result. Unknown fields, missing values, coerced booleans/byte counts, revoked/expired/policy-review states and any claimed approval/execution are rejected.

Both registry reads use the same bearer/public key as the byte transport, canonical HTTPS origin, no redirects, identity encoding and no-store headers. Registry responses must be JSON, at most 8192 raw bytes, complete, unambiguous and within a five-second deadline. Current-state checks allow at most 30 seconds of age and five seconds of forward clock skew. The entire registry/read/recheck operation has a 25-second deadline, including the existing 15-second byte-read bound.

After verifying the bytes, the server reloads current state. Every immutable field and retention-policy identity must match, the registry check time cannot regress or predate the byte check by more than the five-second clock-skew allowance, and retention must remain current through completion. A newly revoked artifact, policy or session prevents a receipt. This is an observation around a read, not a database lock or durable authorization: a later revocation may still invalidate it. Approval must perform its own locked rechecks.

The result adds the registry verifier version, reviewed retention-policy identity and registry check timestamp. `verification_persisted=false`, `scan_status=not_scanned`, `content_approved=false` and `execution_authorized=false` remain explicit. No document bytes, URLs, upstream error bodies or credentials are returned. The registry remains pending_verification and no audit or review record is silently changed.

Tests use bounded synthetic streams and an isolated PostgreSQL adapter. The database workflows exercise the actual registry RPC and object RLS, deny another workspace before retrieving bytes, and revoke an artifact or session during streaming to prove no receipt escapes. Storage HTTP and JWT validation remain simulated; no provider acceptance is claimed.

Next integration must preserve this trust boundary: a user-callable RPC accepting `bytes_verified=true`, a hash or this transient receipt would let a caller fabricate verification. Durable verification needs an explicitly trusted server/worker attestation path, restricted privileges and immutable provenance, with transaction locks/rechecks against the artifact, session, policy, retention and exact review sources. Neither the current client-supplied evidence references nor this internal observational receipt may be treated as a persisted approval credential. Upload/quarantine, scanning, legal holds, purge reconciliation and the guided upload/selector remain open.

## Implemented bounded upload and uncertain-outcome recovery

`AcquisitionStore.upload_evidence` is an internal streaming seam, not a public upload endpoint. It resolves the existing artifact through the protected registry before consuming the source. It buffers at most the registered byte count (bounded by 10 MiB) in process memory, checks exact byte count/SHA-256 and basic format markers, then reloads registry state before the write. No caller filename, object path, URL, replacement flag or alternate bucket is accepted. It creates no temporary file and closes sources that support async close. Empty-chunk flooding and slow input are bounded by a ten-second input deadline; the entire upload/reconciliation path is bounded at sixty seconds.

PDF/PNG/JPEG checks only inspect recognizable boundary markers; plain text must be UTF-8 without prohibited control bytes. These checks are not full parsers, malware scans or permission to open a document. Malformed or malicious files that pass a signature check remain possible. Storage remains unverified; scanning/quarantine acceptance and safe preview are still required.

The transport follows the [documented standard binary upload](https://supabase.com/docs/guides/storage/uploads/standard-uploads), with the same user bearer/public key, exact registered media type/content length, `x-upsert=false`, no-store and no redirects. Standard uploads support the 10 MiB application bound, but the provider recommends resumable uploads above 6 MB; actual size/network acceptance remains a release test. Alternate resumable protocols are not enabled by the current policies.

Each invocation attempts at most one Storage POST. It never deletes, overwrites or silently generates another artifact identity. A successful provider response, a duplicate response, a timeout/connection failure or a server error is not treated as stored-byte proof. Eligible uncertain outcomes are reconciled once by the registry-backed authenticated byte verifier. A conflict or lost reply can return `stored_unverified` only when that read proves the exact registered bytes under current access. The response says `write_outcome=stored_or_existing`, never claims the request created a new object, and retains false persisted-verification/approval/execution flags plus `scan_status=not_scanned`. If confirmation fails after attempting the write, `EvidenceUploadUnconfirmed` requires preserving the same artifact and exact file for recovery. Authorization failures and redirects are not followed or bypassed by a recovery read.

The local database adapter now matches the current official [Storage createObject insert](https://github.com/supabase/storage/blob/master/src/storage/database/pg.ts) without RETURNING. An initial adapter used RETURNING, which correctly activated SELECT RLS and failed under the upload operation. A regression assertion preserves that denial; no read policy was widened. The actual provider's preflight/final caller-permission probes and privileged object finalization in [Uploader](https://github.com/supabase/storage/blob/master/src/storage/uploader.ts) are not fully emulated. Real Storage HTTP/JWT acceptance remains required.

Synthetic tests cover duplicate/concurrent uploads, commit followed by lost/error/timed-out response, wrong/oversized/truncated/type-mismatched input, empty-chunk flooding, revoked/changed registry state, ambiguous outcomes, no redirects/overwrite, and source/response closure. Disposable PostgreSQL workflows prove one object record after retry, cross-workspace denial before input consumption, and current activation enforcement when the gate changes during input reading. No actual file, provider upload, public route or approval was introduced.

Next: controlled registration/upload/state/revocation HTTP contracts with rate and concurrency limits, trusted persisted verification and scan/quarantine lifecycle, locked approval binding, then a guided file picker/recovery panel within the existing numbered mail-review step. The picker must preserve artifact identity and exact-file matching across unknown outcomes; it must not label these uploads approved or safe to open. Retention administration, legal holds and audited purge reconciliation remain open.

## Shared upload admission and process capacity

Local additive migration `20261029142852_acquisition_evidence_upload_admission.sql` adds a private operational slot table and authenticated public-invoker/private-definer reservation function. It reuses existing workspace, profile and composite artifact identities, with RLS and no application-role table privileges. At most two rows can exist per workspace. Expired slots are reused; they are operational capacity records, not evidence/audit history or a change to file-retention policy. Current metadata check still finds no production registry/slot table and latest migration 20261023221455.

Initial engineering limits are deliberately conservative: two reservations per workspace, one per actor within that workspace, each occupying capacity for 120 seconds. There is no client release or renewal. These are fixed operational limits, not legal retention periods; changes require a reviewed migration and capacity testing. Serialization uses a workspace advisory transaction lock, followed by fresh actual session/profile/membership/workspace, creator, campaign, purpose, policy, retention, revocation and acquisition-gate checks. Each server invocation generates a fresh attempt identity and makes one RPC request. A lost response is not replayed or interpreted as permission; capacity may remain occupied until expiry, but no bytes are consumed. Reusing a recorded attempt is rejected. Busy responses carry a bounded retry interval. Application roles cannot inspect/reset slots or reduce expiry. Storage RLS and actual-byte verification remain independent and are rechecked by the upload transport.

`AcquisitionStore.upload_evidence_with_admission` acquires a non-blocking process-wide four-upload semaphore, reserves shared capacity, then invokes the existing bounded upload transport. It closes unread sources on admission failure, releases process capacity on success/error/cancellation, and wraps the operation in a 90-second deadline. An accepted receipt must be fresh within 15 seconds (five-second future clock tolerance), scoped to the exact fresh request, and expire exactly 120 seconds after its database timestamp. It is not a reusable browser token. The existing transport remains limited to 60 seconds and 10 MiB. Deployment memory planning must account for worker count and temporary transport copies.

A 429 response can be presented as “Upload capacity is occupied; try again shortly” with its retry interval. Preserve the existing artifact and exact file; do not create another evidence record to evade the wait. Fast successful uploads still occupy their shared slot until expiry. This intentionally trades initial throughput for bounded failure recovery; early release and higher throughput require separate tested controls.

No HTTP byte-upload route is exposed yet. The low-level transport remains internal for verification and isolated testing; the future public route must use the guarded orchestrator, never call the transport directly. This control limits application upload work; it does not claim to rate-limit direct calls to Supabase Storage, privileged/platform actors or all read operations. ## Guarded HTTP upload contract

`POST /api/acquisition/workspaces/{workspace}/campaigns/{campaign}/evidence/{artifact}/bytes?purpose=mail_content` accepts the original registered file as `application/octet-stream`. Registration and current policy selection happen first. The protected registry remains authoritative for expected digest, length and actual media type; transport headers cannot change those expectations. This endpoint has a separate default-closed `ACQUISITION_EVIDENCE_UPLOAD_ENABLED=true` gate in addition to the existing acquisition gate and database authorization. No environment or production flag was changed.

The handler takes a raw Request stream; it never uses multipart parsing, filename fields, temporary files or a whole-body convenience read. Purpose is the only query parameter and must occur once. Rejects ambiguous/unsupported content types, compressed bodies, caller filenames, malformed/duplicate/zero content lengths and declared sizes above 10 MiB before shared admission or body reads. A missing Content-Length permits bounded streaming; actual bytes must fit the registered size, 10-MiB maximum and any supplied declared length. Streamed length mismatch and a disconnect before completing input are not accepted. The transport still buffers only the bounded original bytes before attempting a non-overwriting write.

The route invokes only `upload_evidence_with_admission`, preserving shared reservations and process capacity. Busy or uncertain-admission outcomes leave the source unread; 429 preserves Retry-After. Before-write preparation failures return 409 with `EVIDENCE_UPLOAD_NOT_ACCEPTED`. Possible-write/verification failures and malformed successful receipts return 503 with `EVIDENCE_UPLOAD_UNCONFIRMED`; preserve the existing artifact and exact file. A client losing the API reply must likewise treat the outcome as unknown and reconcile the same file after any capacity hold. No request retries, overwrite, deletion or new artifact identity are automatic.

Successful receipts are strictly validated for exact scope/purpose, allowed version/type fields, digest/size bounds, recent byte and registry checks, current retention and false persisted-verification/content-approval/execution flags. Result remains `stored_unverified`, `not_scanned`, and `stored_or_existing`; observing matching bytes is not a safe-preview clearance. No download or file rendering route is added. Successful and explicitly handled error responses are no-store. Framework validation and global authentication remain in the existing app infrastructure.

Raw-ASGI tests count receive calls, proving disabled/auth/header/query/capacity denials occur before reading request input. They cover streaming length, size, disconnect, error classification and corrupted receipts. Database-backed workflows cover default closure, workspace denial, stored bytes plus lost provider reply and unavailable verification, capacity hold, exact retry yielding one object, wrong-file rejection and revocation during verification. Storage bytes and provider HTTP remain synthetic; this is not real Supabase Storage/JWT/proxy acceptance. Existing global profile approval and database-identity middleware remain intact and do not consume request bodies.

Deployment acceptance must verify upstream request-size/buffering/time limits as well as these application limits, with fresh approved files in the permitted environment. Keep the upload flag off until that review. Turning it off is the immediate compensation; retain registered artifacts and uncertain-upload identity for reconciliation. The guided picker, trusted persisted verification, scanner/quarantine, locked approval binding and retention administration remain open. ## Durable signed-observation recovery journal

`tools/acquisition_evidence_journal.py` adds a single-host worker journal and `AcquisitionStore.persist_journaled_evidence` dispatches only an already saved request ID. A reviewed worker must prepare the exact signed request once in an operator-provisioned persistent private directory before any dispatch. The directory must be owned by the worker and inaccessible to group/other users; journal symlinks, hard links and broad file permissions are rejected. SQLite uses full synchronous commits and fullfsync where supported, closes each connection, and syncs the initial directory entry. Never place this journal on ephemeral serverless storage or assume it is a distributed queue. Persistent volume, encryption, backup/recovery, quotas and retention controls remain deployment acceptance work. No deployment configuration was changed.

The request body is immutable by ID, including original actor/session, observation text, signature and timestamps. Equivalent envelope key ordering is accepted; changing any value under the same identity is rejected. Dispatch first commits `unconfirmed`, then uses the existing bounded user-authorized transport. A process exit, cancellation, lost response, denied retry or failed confirmation commit retains the original request. Deliberate retries use the same ID/body and current caller credentials; they never resign, renew scope, switch to service credentials or use local confirmation as current authorization. Local confirmation only records the non-approving database receipt. The public scanner/worker route and scheduled execution remain unimplemented and disabled.

### Discovering unfinished work after restart

`EvidenceJournal.pending(workspace_id, actor_id, after=None, limit=50)` reads prepared or unconfirmed requests without requiring a retained in-memory ID list. It returns at most 100 minimal references (request, campaign, artifact, original session and state), plus a scoped cursor. Signatures and signed observation text remain behind `load`. Confirmed entries and other workspace/actor scopes are excluded; corrupt records fail closed. An additive SQLite expression index supports recovery on existing journals without replacing their requests. This is trusted worker storage, not user authorization or an exposed HTTP endpoint.

A recovery pass does not reserve, renew, sign, dispatch, delete or approve anything. Load each selected original request, obtain appropriate current user-scoped credentials and deliberately invoke `persist_journaled_evidence`; preserve the original session identity and request body. Revoked/expired original authority may prevent a new write, while only the database can confirm an exact historical duplicate. New IDs may sort before an active cursor, so later sweeps restart at the beginning rather than treating a page cursor as a permanent watermark. Persistent scheduling, worker admission, quota/retention and deployment acceptance remain open.

### Bounded admission

New journal requests are capped at 10,000 records, each with the existing 12 KiB serialized-request bound. Admission and insertion share the SQLite write transaction, so concurrent preparers cannot overfill the record cap. The cap includes confirmed history; exact existing requests still prepare/reconcile at capacity. Nothing is automatically purged, replaced, resigned or moved to another journal. Capacity exhaustion requires operational review and a separately designed retention/archive procedure. This record cap does not replace filesystem quotas, persistent-volume monitoring or audited retention controls.

### Original destination binding

Before the first dispatch, the journal saves the canonical authenticated HTTPS REST base URL in the same transaction as the uncertain state. Every later attempt must use that exact destination. Changing worker configuration cannot replay a saved signed request to a different project. Concurrent first attempts cannot bind two destinations. Current credentials are validated before the dispatch marker; no credentials are stored.

Existing journals receive an additive nullable destination column. Prepared requests can bind their first destination. Older unconfirmed/confirmed requests without destination evidence stay readable and discoverable but cannot dispatch: they require review of original worker configuration and an explicitly reviewed recovery procedure. Never guess the endpoint, erase the request, change its identity or bind it automatically from the current configuration. No production worker or journal was migrated by this code change.
